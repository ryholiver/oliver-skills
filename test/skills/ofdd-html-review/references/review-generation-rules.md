# 基于 OFDD 的 Review 生成与回写规则

> 版本：v2 · 2026-08-19  
> 用途：规定 AI 或人工如何围绕特定目标、任务或需求，从 OFDD 项目实例中生成 Review，并将 Review 结果回写 OFDD。  
> 上游框架：OFDD 认知决策数据，由用户输入或上游 skill 提供。  
> 下游框架：已拍板决定可进入计划、执行与反馈闭环。  
> 应用层模板：`../assets/review-template.html`。  
> 当前边界：本文件定义 Review 的内容与逻辑规则；HTML 模板负责应用层展示，不作为独立事实源。

---

## 一、Review 的定位

Review 不是一套独立本体，也不是新的项目事实源。

Review 是围绕某个具体目标、任务或需求，对 OFDD 项目实例进行筛选、组织、验证和决策的一次应用过程：

```text
OFDD 项目实例
+ 本次目标 / 任务 / 需求
+ Review 规则
→ 特定 Review
→ 讨论、确认或拍板
→ 新来源 / 新观察 / 状态变化 / 新决定
→ 回写 OFDD
```

二者分工：

```text
OFDD 管理：我们知道什么、如何知道、如何形成方向与决定。
Review 管理：针对这次问题，需要看什么、确认什么、比较什么、决定什么。
```

同一份 OFDD 可以根据不同目标生成多份 Review；一份 Review 只展示当前问题所需的最小认知集合，不复制整个 OFDD。

---

## 二、基本原则

### 2.1 单一认知事实源

1. OFDD 项目实例是认知与决策对象的事实源。
2. Review 引用 OFDD 中的观察、推断、判断、疑问、方向和决定，不另行复制一套同义对象。
3. Review 中出现的新信息、状态变化和决定必须回写 OFDD；不得只修改 Review 产物而不更新 OFDD。
4. Review HTML 是面向特定目标生成的展示快照，不作为独立事实源。
5. 执行层只读取 OFDD 的已批准版本；Review 中的新内容不得直接修改当前执行。
6. 需要改变 OFDD 或执行的内容必须经过“暂停 Review → 回写 OFDD → 继承式重启”这一变更闸门。

### 2.2 Review 生命周期与版本

Review 不是一次性页面，而是同一 Review 线上的有版本实例：

```text
Review v1（首次激活）
→ 发现新信息
→ v1 暂停待回写
→ OFDD 版本更新
→ Review v2（继承式重启）
→ 继续当前目标与讨论
```

- `review_id` 标识同一条 Review 线，续轮不变；
- `review_version` 标识该 Review 线的实例版本，续轮递增；
- `parent_review_id` 和 `resumes_from_review_id` 指向上一轮实例；
- `inherited_artifacts` 记录必须承接的目标、范围、结论、判断链、决定和未决项；
- 继承式重启只重算新信息影响的链路，不得把上一轮有效成果清零；
- 旧版实例保留为历史快照，并标记 `superseded` 或 `paused_for_writeback`，不能继续作为受影响执行的依据。

### 2.3 最小必要信息

5. Review 只选择会影响本次判断、方向或决定的关键内容，不逐条背诵全部材料。
6. 如果移除某条内容不会改变本次判断、方向或决定，则默认不进入 Review 主体，可作为支撑信息或附录保留。
7. 关键内容必须保留 OFDD ID 与证据追溯关系；前台可以显示自然语言标签，审计视图再显示完整编号。

### 2.3 事实、观点与时效性

8. 访谈、项目文档、聊天记录、数据和会议纪要属于来源材料，不天然等于客观事实。
9. 来源只能直接证明“材料中出现过某项内容”；观察只能陈述证据直接支持的内容，不把个人观点扩大为整体事实。
10. 对可能影响本次结论的关键观察，应确认：
    - 表述是否忠于来源；
    - 当前是否仍然有效；
    - 是否适用于本次目标和范围；
    - 是否已被更新信息替代。
11. 文档中曾经成立的内容，不自动等于 Review 当下仍然成立。

### 2.4 不确定性允许存在

12. Review 可以展示待验证推断、条件性判断和非阻塞疑问，不要求所有信息确认后才开始讨论。
13. 未确认内容必须声明状态、成立条件和影响范围，不得伪装成已确认结论。
14. 阻塞本次决定的问题应在拍板前处理；不阻塞当前决定的问题可以记录后继续验证。
15. 信息不足时，可以形成“暂缓决定”或“条件性方向”，不得为了给出结论而隐藏不确定性。

## 三、Review 的触发条件与类型

### 3.1 触发条件

出现以下情况之一，可以创建 Review：

1. 需要形成新的方向或决定；
2. 需要重新评估已有方向或决定；
3. 关键观察可能过期、冲突或发生变化；
4. 推断或判断存在争议，需要验证；
5. 阻塞性疑问需要负责人回答；
6. 多个方向需要比较和取舍；
7. 项目目标、范围、约束或评价标准发生变化；
8. 执行或验收产生的新观察触发了重新判断。

### 3.2 Review 类型

| 类型 | 核心问题 | 主要处理对象 | 必须形成决定 |
| --- | --- | --- | --- |
| **认知型 Review** | 我们对问题的理解是否准确？ | 观察、推断、疑问 | 否 |
| **判断型 Review** | 这些信息相对于目标意味着什么？ | 推断、判断、评价标准 | 否 |
| **决策型 Review** | 在多个方向之间选择什么？ | 判断、疑问、方向、决定 | 是，或明确暂缓 |
| **重评型 Review** | 原方向或决定是否仍然成立？ | 新观察、原判断、原决定、重评条件 | 是，需维持、撤销、替代或暂缓 |

一次 Review 可以同时包含多个类型，但必须声明主要类型，防止“只是对齐认知”与“需要现场拍板”混淆。

## 四、Review 的输入

每次 Review 至少声明以下输入：

| 输入 | 说明 |
| --- | --- |
| Review 目标 | 为什么进行这次 Review |
| 当前任务或需求 | Review 服务于哪个项目任务、业务需求或个人需求 |
| 核心问题 | 本次需要回答的一个主要问题 |
| 预期结果 | 对齐认知、验证判断、选择方向或形成决定 |
| 适用范围 | 本次讨论覆盖和不覆盖什么 |
| 评价标准 | 用什么目标、指标或约束评价对象 |
| OFDD 对象范围 | 本次调用的观察、推断、判断、疑问、方向和决定 |
| 参与人与决策人 | 谁提供信息、谁参与讨论、谁有权拍板 |
| 时间基准 | 关键观察需要确认到哪个时间点仍然有效 |

### 4.1 从目标反向选择内容

Review 不从“有哪些资料”开始堆叠，而从“这次要解决什么”反向筛选：

```text
目标 / 任务 / 需求
→ 需要形成或重评什么决定
→ 需要比较哪些方向
→ 哪些判断支持方向比较
→ 哪些推断支持判断
→ 哪些观察和证据支持推断
→ 哪些疑问可能改变上述链路
```

### 4.2 进入主体的判断条件

符合以下任一条件的内容，应进入 Review 主体：

- 会改变关键判断；
- 会改变候选方向；
- 会改变是否拍板；
- 会改变决定的适用范围；
- 会触发已有决定的重评条件；
- 属于本次决定的阻塞性疑问；
- 是关键结论唯一或主要的证据依据。

其余内容进入支撑信息或证据附录，不在主体逐条确认。

## 五、Review 的表达规则

### 5.1 观察如何表达

观察只表达来源直接支持的内容，并保留证据引用。

推荐句式：

> 【主体】在【时间/材料】中表示或记录了【可被证据直接支持的内容】。

示例：

> 张敏在访谈中表示约课渠道包括微信，但更偏向电话，并主张优先打电话。证据引用：E-009。

不得直接扩大为：

> 销售约课的主要渠道就是电话。

除非存在能够支持整体事实的数据或正式规则。

### 5.2 推断如何表达

推断说明从观察中获得的描述性、解释性、因果性或预测性信息。

推荐句式：

> 基于【观察 ID】，当前信息可能说明【推断内容】；需要通过【验证方式】确认，当前状态为【状态】。

示例：

> 基于 O-09 和 O-15，当前企微方案覆盖的交互渠道可能与销售主要约课渠道不完全一致；需要补充渠道业务量和成功率数据，当前状态为待验证。

### 5.3 判断如何表达

判断必须声明评价对象、评价标准、依据、结果和状态。

推荐句式：

> 基于【观察/推断】，相对于【目标、标准或约束】，判断【评价对象】存在或具备【评价结果】；该判断在【成立条件】下成立，当前状态为【状态】。

示例：

> 基于 F-I-01，相对于“是否覆盖真实约课主流程”的标准，如果电话确为主要约课渠道，则当前企微优先方案存在场景范围错配风险。当前状态为待验证。

判断回答“相对于目标意味着什么”，不得直接写成行动指令。

### 5.4 疑问如何表达

疑问必须说明认知缺口、提问目的、影响对象、阻塞性和验证方式。

推荐句式：

> 为了【目标或决定】，需要确认【未知信息】；该问题影响【判断/方向/决定】，当前【阻塞/不阻塞】；建议通过【方式】回答。

示例：

> 为了确定 Q3 产品范围，需要确认 AI 约课实际接管销售流程的哪一段、哪些渠道；该问题不阻塞业务调研和能力储备，但阻塞最终方案范围决定，建议由项目负责人结合合同范围和实际业务数据确认。

疑问应按影响分类。以下分类是 Review 展示方式，由 OFDD 中的“阻塞性 + 阻塞对象”推导，不新增第二套疑问状态：

| 类型 | 处理规则 |
| --- | --- |
| 阻塞本次决定 | Review 拍板前必须处理，无法回答时应暂缓相应决定 |
| 阻塞后续方案 | 可以先决定方向，但不得进入被阻塞的方案或计划范围 |
| 不阻塞推进 | 记录负责人和验证方式，允许当前工作继续 |
| 认知补充 | 放入问题池或附录，不占用主体讨论时间 |

### 5.5 方向如何提出

方向表达为回应判断而选择的行动指向，不是计划和 Todo。

推荐句式：

> 为回应【判断】，建议朝【目标状态】推进，优先覆盖【范围】，暂不覆盖【范围】；该方向依赖【条件】，主要风险是【风险】。

每个候选方向至少包含：

```text
方向名称
回应的判断
目标
包含范围
不包含范围
支持理由
反对理由或风险
依赖条件
当前状态
```

同一 Review 应尽量提出可真实选择的方向，而不是把推荐方向包装成唯一答案。方向之间可以互斥，也可以并行。

### 5.6 决定如何表达

决定必须说明选择、拒绝或暂缓什么方向，并记录依据和约束。

推荐句式：

> 基于【关键判断】，决定【选择/拒绝/暂缓】【方向】；适用范围为【范围】，未决项为【问题】，当【重评条件】出现时重新评估。

决策型 Review 结束时必须形成以下结果之一：

- 选择某方向；
- 拒绝某方向；
- 暂缓某方向；
- 维持原决定；
- 撤销原决定；
- 用新决定替代原决定。

如果没有形成正式决定，必须明确原因、缺少的信息和下一次进入决策的条件。

## 六、Review 的执行流程

### 第一步：声明本次目标

Review 开始时先对齐：

```text
这次为什么 Review？
核心问题是什么？
需要形成什么结果？
讨论范围是什么？
谁有权拍板？
```

没有明确目标时，不进入材料汇报。

### 第二步：给出当前认知摘要

先用最短内容说明：

```text
当前初步结论
关键依据
最大不确定性
当前建议或需要比较的方向
```

摘要中的每个关键结论必须可以追溯到 OFDD 对象。

### 第三步：确认关键观察

只确认可能改变当前判断、方向或决定的观察：

```text
是否忠于来源？
是否仍然有效？
是否适用于当前范围？
是否存在新信息或反例？
```

其余观察不逐条复述，讨论需要时展开证据。

### 第四步：验证推断与判断

依次检查：

```text
观察是否足以支持推断？
是否存在其他合理解释？
判断使用了什么评价标准？
评价标准是否符合本次目标？
判断的成立条件是否满足？
当前状态应如何更新？
```

### 第五步：处理疑问

1. 先处理阻塞本次决定的问题；
2. 再记录阻塞后续方案的问题；
3. 不阻塞问题不占用不必要的现场时间；
4. 新回答应保留为可定位的会议记录或其他来源，不能只留下口头印象。

### 第六步：比较方向

候选方向至少按以下维度比较：

```text
与目标的匹配度
支持它的判断
反对它的判断
覆盖范围与边界
依赖条件
主要风险
时间与资源约束
不选择的代价
```

不同 Review 可以增加项目特定维度，但不得在看到结果后无声更换评价标准。

### 第七步：形成结果

决策型或重评型 Review 必须记录：

```text
选择、拒绝或暂缓的方向
决定状态
决策人
决定时间
适用范围
依据
未决项及阻塞性
重新评估条件
```

认知型或判断型 Review 至少记录：

```text
哪些观察被确认或修正
哪些推断和判断状态发生变化
哪些疑问被回答或新增
是否达到进入方向或决策阶段的条件
```

## 七、Review 的输出结构

HTML 模板后续单独实现，但所有输出载体都应包含以下内容结构：

```text
1. Review 基本信息
2. 本次需要解决的问题
3. 当前核心结论
4. 关键观察与证据
5. 关键推断与判断
6. 待回答问题及阻塞性
7. 方向选项比较
8. 建议方向
9. Review 结果或决定
10. 未决事项与重评条件
11. OFDD 回写清单
```

### 7.1 第一屏信息优先级

面向普通参与者时，优先展示：

```text
这次要决定什么？
当前怎么看？
为什么这样判断？
还缺什么？
有哪些方向？
建议选择什么？
```

证据 ID、完整原文和技术字段可以折叠展示，但不得删除底层关联。

### 7.2 HTML 展示边界

未来 HTML 输出应遵守：

1. 默认显示人类可读 label，不强制展示裸 ID；
2. 悬停证据时优先展示 `quote_snapshot`；
3. 点击证据时通过 `source_id + anchor` 跳转完整上下文；
4. 判断、疑问、方向和决定使用不同视觉层级；
5. HTML 是特定时间点的 Review 快照，不允许成为独立事实源；
6. 内容变化应先更新 OFDD，再重新生成或同步 Review HTML。

## 八、Review 结果回写 OFDD

### 8.1 回写流程

Review 现场产生的新内容按以下顺序处理：

```text
Review 录音 / 纪要 / 确认记录
→ Source
→ Evidence Reference
→ Observation
→ 更新 Inference / Judgment / Question 状态
→ 更新 Direction
→ 新增或更新 Decision
```

### 8.2 回写规则

1. 现场回答首先作为新的来源内容，不直接覆盖旧观察。
2. 新回答与旧观察冲突时，保留历史，并通过新观察和状态变化表达更新。
3. 推断或判断状态变化必须记录触发证据、日期和原因。
4. 已回答疑问必须链接支持答案的新观察，不以“会上确认了”代替证据。
5. 决定变更不得覆盖历史决定，应标记为撤销或已替代，并链接新决定。
6. 已拍板决定进入《决定执行与反馈闭环》；存在阻塞性未决项时，只能进入不受阻塞的执行范围。

## 九、Review 质量检查

AI 或人工生成 Review 后，应检查：

### 9.1 目标检查

- 是否明确本次 Review 要解决的问题？
- 是否明确预期结果是对齐、判断、决策还是重评？
- 是否明确适用范围和决策人？

### 9.2 认知检查

- 是否把来源中的观点误写成客观事实？
- 关键观察是否有证据引用？
- 是否区分了观察、推断和判断？
- 判断是否声明评价对象和评价标准？
- 待验证内容是否声明状态和成立条件？

### 9.3 决策检查

- 问题是否说明阻塞对象？
- 是否处理了阻塞本次决定的问题？
- 方向是否说明目标、边界、依赖和风险？
- 是否存在可真实比较的方向选项？
- 决定是否明确选择、拒绝或暂缓什么？
- 是否记录未决项和重新评估条件？

### 9.4 追溯检查

- Review 关键结论是否能回到 OFDD ID？
- 是否能沿着判断、推断、观察、证据引用追溯到来源？
- Review 新信息是否已经列入 OFDD 回写清单？
- HTML 或其他展示产物是否被错误地当成新的事实源？

## 十一、销售 AI 约课项目的最小示例

### 11.1 Review 目标

```text
Review 类型：决策型
目标：确定 2026-08-31 前销售 AI 约课项目的推进方向和验收边界
核心问题：当前应只推进企微文本闭环，转向电话语音，还是采用双线并行？
评价标准：短期生产闭环、合同范围、真实业务价值、技术与时间风险
```

### 11.2 关键认知链路

```text
观察 O-09：
张敏表示约课渠道包括微信，但更偏向电话，并主张优先打电话。
证据引用：E-009。

观察 O-15：
项目合同要求首批销售通过企微承接真实线索并产生可追踪链路。
证据引用：E-015。

推断 F-I-01（待验证）：
当前企微方案覆盖的交互渠道可能与真实主要约课渠道不完全一致。

判断 F-J-01（待验证）：
相对于“是否覆盖真实约课主流程”的标准，如果电话确为主要渠道，当前企微优先方案存在场景范围错配风险。
```

### 11.3 关键问题

```text
问题 F-Q-01：
为了确定最终产品范围，需要确认 AI 约课实际接管销售流程的哪一段、哪些渠道。
阻塞性：不阻塞业务调研和语音能力储备；阻塞最终方案范围决定。

问题 F-Q-02：
为了形成无歧义验收标准，需要确认 2026-08-31 前的 Q3 验收范围。
阻塞性：阻塞最终验收范围决定。
```

### 11.4 方向比较

| 方向 | 目标 | 主要优势 | 主要风险 |
| --- | --- | --- | --- |
| 企微文本优先 | 集中完成短期生产闭环 | 范围集中，短期交付风险较低 | 可能无法覆盖真实主要渠道 |
| 电话语音优先 | 优先验证主要业务渠道 | 更接近真实约课场景 | 技术复杂度和短期交付风险较高 |
| 双线并行 | 企微闭环与语音储备同时推进 | 兼顾短期交付和长期价值 | 资源可能分散，需要明确两条线边界 |

### 11.5 Review 结果表达

```text
建议方向：DIR-04，业务推进与语音能力储备并行。

决定状态：当前实例记录为已拍板，但决策人、精确时间和完整判断依据待补。

未决项：
- F-Q-01 不阻塞调研和能力储备，阻塞最终方案范围；
- F-Q-02 阻塞最终验收口径。

重新评估条件：
负责人 Review 后形成可定位的范围和验收记录，或新的渠道数据推翻 F-I-01。
```

该示例只演示 Review 如何调用 OFDD，不在 Review 中复制或替代 OFDD 项目实例。

## 六、执行影响分流与继承式重启

### 6.1 新信息的三类分流

| 执行影响 | 处理动作 | 是否暂停当前 Review | 是否回写 OFDD |
| --- | --- | --- | --- |
| `none` | 作为展示补充或候选内容保留 | 否 | 可不回写 |
| `potential` | 标记风险，纳入回写清单 | 否 | Review 结束后回写 |
| `blocking` | 冻结受影响执行范围，提交 OFDD 变更 | 是 | 立即回写后再续作 |

`blocking` 不仅指“已经证明计划错误”，也包括可能改变当前决定、范围、验收标准、依赖关系或执行前置条件的高影响新信息。

### 6.2 继承式重启的固定步骤

1. 将当前 Review 实例标记为 `paused_for_writeback`；
2. 在 OFDD 中新增来源和证据，或更新受影响的观察、推断、判断、方向、决定和 `review_gate`；
3. 递增 `ofdd_version`，记录变更原因和受影响执行范围；
4. 暂停或冻结受影响的执行项，未受影响的执行项可继续；
5. 基于新 OFDD 生成同一 `review_id` 的下一版 Review；
6. 复制上一版仍有效的目标、范围、结论、决定、未决项和回写清单；
7. 仅重算受新信息影响的链路，并将新实例标记为 `resumed_inherited` / `inherited_resume`；
8. 通过新的 Review Gate 确认哪些执行项可以恢复、哪些需要重新规划。

### 6.3 不允许的捷径

- 不允许只改 HTML 而不更新 OFDD；
- 不允许把 `extra_*` 中的候选内容直接当作执行指令；
- 不允许用新 Review 覆盖旧 Review，必须保留父子版本关系；
- 不允许因为 Review 已经重新生成，就默认恢复全部执行；恢复必须由新的 OFDD `review_gate` 明确授权。
